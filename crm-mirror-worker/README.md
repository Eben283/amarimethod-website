# Amari CRM mirror worker

This Worker is the owned data foundation for the internal Amari CRM. Its bounded five-minute import sweep reads GHL and Stripe into D1 and never writes back to either provider. Separately, a Worker-authenticated appointment command seam can durably capture a provider-neutral Staff scheduling decision; capture does not send, book, or fall back to GHL. The authenticated Staff Client Desk mirrors records and relays an approved SMS reply through the signed Staff sender.

## What it mirrors

- GHL contacts, tags, custom-field values, and contact appointments.
- Stripe settled charges and refund metadata.
- Review-only purchase-to-contact candidates when one Stripe billing email exactly matches one mirrored contact.
- Existing service and package definitions seeded by the first D1 migration.

Migration `0019_owned_appointment_authority.sql` preserves all existing appointment, note, session-ledger, and provider-observation identities while making the canonical appointment ID provider-independent. It adopts and rebuilds the populated production-only `appointment_source_observations` child so its restrictive appointment foreign key follows the replacement parent instead of blocking or corrupting the migration. It also adds the appointment command/event ledger and owned service collision policy used by `POST /appointments/commands`. That protected route captures schedule intent, leases one executor, and records exact provider-link, compensation, completion, retry, rejection, or manual-review evidence. It never calls a provider. The first Staff integration uses it only for Partner Initial scheduling while the isolated GHL calendar adapter remains the temporary propagation edge.

Migration `0020_owned_appointment_lifecycle_dispatch.sql` adds the durable Partner Initial lifecycle outbox. An exact provider readback, the owned appointment update, command completion, and the immutable outbox payload digest commit in one D1 batch. The five-minute sweep leases each row and hands it to `reminder-engine` through the `REMINDER` service binding using Worker authentication; failures retry, digest or semantic drift is quarantined for review, and the reminder engine's own enrollment key makes crash recovery idempotent. The reminder flow remains shadow-only: this handoff records lifecycle evidence but cannot deliver a reminder.

Migration `0021_provider_neutral_calendar_authority.sql` preserves existing GHL command/outbox rows while allowing an exact `google_calendar` appointment link and a nullable provider-contact field for that edge. Schedule, reschedule, and cancellation lifecycle evidence all use the owned appointment/contact/service identities; provider appointment/calendar IDs remain evidence in event context instead of becoming lifecycle identity. The Pages adapter remains GHL by default. Only the in-person `partner-initial` service can select the new edge, and only when all three server variables are explicit: `STAFF_APPOINTMENT_CALENDAR_PROVIDER=google_calendar`, `STAFF_APPOINTMENT_GOOGLE_CALENDAR_ID=<exact writable calendar id>`, and `STAFF_APPOINTMENT_GOOGLE_USER=<exact OAuth grant owner>`. Every Google mutation sets `sendUpdates=none`, creates no attendee, disables Calendar reminders, stores only opaque owned IDs in private extended properties, and requires exact readback. Other services remain on their current GHL adapters until separately migrated.

Migration `0022_partnership_discovery_service.sql` adds the exact existing Partnership Discovery calendar as an owned service identity. Staff scheduling captures the owned appointment command before using the unchanged GHL edge. It deliberately creates no generic Discovery lifecycle dispatch: GHL remains responsible for `ambassador-prospect`, the Partnership Pipeline, attendance/promotion decisions, notifications, and the complimentary Partner Initial handoff until that complete contract is migrated as its own reviewed slice.

Migration `0023_owned_quiz_intake.sql` adds append-only normalized source evidence for the Pain Pattern Quiz. The Worker-authenticated `POST /contacts/quiz-intake` boundary resolves exactly one owned contact by normalized email (or creates a deterministic owned identity), records the current lead role, quiz tags, and provider-neutral contact attributes under `owned:quiz`, and refuses ambiguous identity or idempotency drift. In the same D1 transaction it appends a digest-bound lifecycle outbox row. The bounded five-minute sweep leases that row and hands the exact owned contact event through the authenticated `NURTURE` service binding; only an exact Flow 1 `enroll`/idempotent `enroll-noop` acknowledgement closes it. Failures retry and digest/cross-flow drift enters manual review. Every nurture sequence remains shadow-only, so this creates observation state but cannot send. The public Pages client is intentionally not connected in this source slice; GHL remains the live quiz intake until the sensitive server-to-server payload seam receives separate review and approval.

Migration `0024_owned_email_dispatch_control.sql` adds the next provider-neutral Staff communication boundary without activating it. Exact actor-bound email commands, mutable queue control, and append-only transition evidence are separate records. Commands captured while source mode is `shadow` become terminal `shadow_blocked` evidence and can never be promoted into a pending send later; policy-blocked commands are equally terminal. The future active path re-resolves the owned contact destination, current channel consent, DND, archive state, actor allowlist, and content digest after an atomic claim but before provider I/O. Only an explicitly retryable pre-acceptance failure may retry. A Gmail-accepted submission that cannot write its exact CRM proof becomes `submission_unreconciled` and is never retried into a duplicate. Both Eben and Garrett are bound to their own exact Amari Workspace mailboxes. Provider submission is not labeled delivery, no SMS adapter or GHL fallback exists, and `OWNED_EMAIL_SOURCE_MODE` is hardcoded `shadow`; environment variables cannot activate this revision.

Migration `0025_appointment_recovery_requests.sql` adds a narrow, provider-neutral missed-appointment review boundary. A recovery-only signed appointment link may append one `pending_review` request for the exact owned appointment, contact, and revision after both Pages and CRM independently confirm current `no_show` state and ready authority. Replay is idempotent, request/event identity is immutable, and Staff receives a bounded read-only queue. This path cannot book or alter an appointment, grant a session or credit, charge a payment, send a message, or decide the request.

Migration `0026_owned_missed_appointment_truth.sql` replaces the future need for GHL's mutable “Missed Appointments” counter with provider-neutral appointment facts. It backfills existing canonical appointments as explicitly incomplete baselines, appends one immutable fact per later appointment revision, and derives each person's current no-show count from the latest revision. A correction such as `no_show` → `attended` appends evidence and removes that appointment from the derived count without rewriting history. The protected `/appointments/missed-truth` route is read-only, reports missing/mismatched/baseline coverage, and treats any ingested GHL contact-field number as comparison evidence—not authority. The migration and route are source-only until separately installed and released.

Migration `0027_owned_appointment_attendance.sql` adds the provider-neutral write side for that truth without activating it. One idempotent Staff command may change only an exact-revision appointment whose authority is already `owned` and whose provider sync state is already `not_required`. The same atomic D1 statement appends command/result evidence, updates the canonical status and revision, and invokes the immutable status-fact trigger. A later `no_show` → `attended` correction is another command and revision; a same-status request reserves its idempotency key without revising truth. Database guards reject provider mirrors, stale revisions, archived contacts, cancelled appointments, missing start times, and premature marking. The source-pinned `/appointments/attendance-commands` route always returns `owned_attendance_shadow_only` in this revision, even if an environment variable claims activation. The command has no provider, session-ledger, entitlement, payment, message, or recovery-decision effect.

Migration `0028_owned_note_authority.sql` adds provider-neutral Staff notes as immutable revision history without activating writes. Create, revise, archive, and restore commands bind the exact contact, optional owned appointment, named Staff actor, prior revision, body digest, and idempotency key. Database guards reject archived contacts, cross-contact appointments, stale revisions, identity drift, and invalid state transitions; update and delete are forbidden. Current active owned notes can join provider-mirror notes in the Client Desk read model, while a missing schema degrades to the existing provider read rather than breaking the Desk. The browser-only `POST /notes/commands` route requires a same-origin signed Eben or Garrett session, refuses provider fields, and remains source-pinned `owned_note_shadow_only` in this revision. It has no provider, message, payment, appointment, entitlement, destructive-delete, or authority-promotion effect.

Migration `0029_owned_task_authority.sql` adds provider-neutral Staff tasks as immutable revision history without activating writes. Create and revise commands require an explicitly zoned due time or an explicit null; complete, reopen, archive, and restore preserve the exact task definition while recording each state transition. Archive remembers whether the task was open or completed so restore cannot silently change completion truth. Exact actor/idempotency/revision, active-contact, optional appointment, content digest, and database transition guards reject stale or cross-contact writes and forbid update/delete bypass. Current non-archived owned tasks join provider-mirror tasks in the Client Desk record and timeline, while absent schema safely retains the provider read. The same-origin `POST /tasks/commands` route requires a signed Eben or Garrett session, refuses provider fields, and remains source-pinned `owned_task_shadow_only`. It has no provider, customer-message, payment, appointment, destructive-delete, or authority-promotion effect.

Migration `0030_owned_contact_classifications.sql` adds provider-neutral Staff-owned roles and tags without activating writes. Each add/remove or grant/revoke is immutable, actor-bound, idempotent evidence; only the current `owned:staff` projection is materialized in the existing role/tag tables. Exact replay of an old removal cannot undo a later addition because only a newly inserted command fires the projection trigger. Provider-sourced classifications remain untouched, and contact reads deduplicate labels that both sources currently assert. Database guards reject archived contacts, forged result state, evidence mutation, invalid roles, and malformed canonical tags. The same-origin `POST /contacts/classification-commands` route requires a signed Eben or Garrett session, refuses provider identity, and remains source-pinned `owned_classification_shadow_only`. It has no provider, customer-message, payment, appointment, deletion-of-evidence, or authority-promotion effect.

Migration `0031_owned_contact_profile_authority.sql` adds provider-neutral Staff authority for contact names, email destinations, and phone destinations without activating writes. Each field family has an independent revision and authority flag, so owning a name cannot silently promote a communication destination. A new email or phone records immutable before/after command evidence and a consent observation bound to that exact normalized destination and digest; consent for an old or provider-mirrored destination cannot authorize it. Later GHL and quiz imports preserve any field family already owned while continuing to refresh provider-mirror fields. All communication and reminder reads require exact destination-bound consent once the destination is owned. The same-origin `POST /contacts/profile-commands` route requires a signed Eben or Garrett session, rejects provider or side-effect fields, and remains source-pinned `owned_contact_profile_shadow_only`. It cannot create a contact, call a provider, send a message, change an appointment or payment, delete evidence, or promote runtime authority. Because this migration alters populated core tables, it is a separate future schema-review gate rather than part of the additive v22-to-v30 installer.

Stripe charges that cannot be linked to a mirrored GHL contact are retained as unlinked purchase candidates. Package balance is deliberately **not** written to `session_ledger_entries` yet: a full ledger backfill must reconcile purchases against explicit attendance and refunds, rather than guessing from a mutable GHL field.

An email candidate is evidence for staff review, not a purchase link. The importer never turns it into `purchases.contact_id`, never posts a ledger entry, and never sends a message.

## Provisioning and deployment

**Do not run `wrangler deploy` directly.** Every CRM Mirror release must use the repository-root command below from a clean checkout at the exact reviewed `origin/main` SHA:

```bash
npm run deploy:crm-mirror -- --deploy --approved-revision <full-origin-main-sha>
```

The command refuses a dirty or non-`origin/main` checkout, SHA-256 hashes the exact archived `crm-mirror-worker` source, deploys with `--strict --keep-vars`, then reads the resulting Worker version back. The Cloudflare Worker version tag/message are the durable release record and must contain both `git_sha=<40-char SHA>` and `artifact_sha256=<64-char SHA-256>`. A missing or mismatched record fails the release. `npm run deploy:crm-mirror` without `--deploy` is a non-writing preflight.

The supported production path is the protected **deploy CRM Mirror** GitHub Actions workflow, dispatched from current `main`; it uses the dedicated `CLOUDFLARE_CRM_MIRROR_DEPLOY_TOKEN` repository/environment secret. This repository guard deprecates arbitrary local Wrangler releases. It cannot prevent a user who deliberately bypasses the command and retains broad Cloudflare deploy credentials; enforce that boundary by moving the Worker deploy identity to scoped GitHub Actions and withdrawing broad local Worker-deploy authority in a separately approved Cloudflare access change.

The dedicated `amari-crm-mirror` D1 database is bound in `wrangler.jsonc`; its initial schema migration has been applied. The scheduled sweep advances each provider cursor with a bounded read. An authenticated `POST /sync` remains available for an operator-requested import.

`/status` reports separate GHL and Stripe health states, treating a paginated GHL pass as healthy while it advances through the cursor; a source is stale after 45 minutes.

The five-minute sweep first drains bounded owned appointment lifecycle evidence, shadow quiz-nurture handoff, and the source-disabled Staff email lane before reading the newest three GHL conversations. It then rotates one bounded
provider lane: current GHL contacts/appointments, Stripe charges/invoices, or
historical GHL conversation/client enrichment. Every core source is therefore
attempted at least once per fifteen minutes, inside the 45-minute freshness
contract, without combining hundreds of provider/database subrequests into one
invocation. GHL pacing queues are invocation-scoped; a terminated cron cannot
leave a dead promise in a warm isolate and poison later syncs.

Appointment readiness keeps exact `sync_initial` snapshots as visible
historical baselines with incomplete history; it does not rename them create
events. It also recognizes an older provider-mirror row only when its exact
external-record receipt matches the same pre-projection importer timestamp.
Those accepted baselines do not count as current conflicts. The GHL projection
reconciles only appointments with an exact GHL crosswalk; provider-neutral
owned appointments are reconciled separately against their command, completion,
and exact provider-link evidence in the append-only authority ledger. Unsynced,
incomplete, receipt-mismatched, orphaned, colliding, or truncated evidence
remains blocking in the ledger that owns it.

Dashboard: open from Staff → Back office → CRM Mirror (Eben-only). That path calls `POST /api/staff-crm-mirror-access`, which mints a one-time `/dashboard-access/:code` handoff server-side. Direct worker URL visits without a session show a locked shell and never accept a pasted bearer secret in the browser. Full-pass completeness ignores GHL contacts confirmed deleted at the source so ghost `external_records` do not keep the mirror in review.

Worker secrets must always be configured outside source control: `WORKER_AUTH_SECRET`, `STRIPE_SECRET_KEY`, `GHL_CLIENT_ID`, `GHL_CLIENT_SECRET`, `AMARI_MAIL_GOOGLE_OAUTH_CLIENT_ID`, and `AMARI_MAIL_GOOGLE_OAUTH_CLIENT_SECRET`. Each signed Staff actor's mail authorization is isolated under `amari-mail:eben:*` or `amari-mail:garrett:*` in `PORTAL_KV`; it must never reuse a shared mail grant, the `google:eben:*` Calendar grant, or the general `GOOGLE_OAUTH_CLIENT_ID` / `GOOGLE_OAUTH_CLIENT_SECRET` credentials. The Gmail adapter requires that actor's verified grant-status marker before reading any token. The Staff browser never receives these credentials. Owned delivery remains disabled until the readiness blockers are cleared and independently verified.

`GET /api/staff-amari-mail-auth` reports the signed actor's non-delivering grant readiness. `POST /api/staff-amari-mail-auth` starts a signed, one-time consent flow for that actor's own exact mailbox; `/api/staff-amari-mail-callback` verifies the exact Gmail profile and SendAs identity before storing the isolated grant. These routes do not expose a composer, dispatch a message, or provide a GHL fallback.

If this Worker is recreated, create a new dedicated D1 database and replace the binding ID before deploying. Never reuse the live automation database.

## Authenticated endpoints

- `GET /status` — counts and last sync result; no client data.
- `GET /readiness` — aggregate completeness, current source health, recovery evidence, and open exception counts; no client data and no sync trigger.
- `GET /reconciliation` — aggregate pending-review counts; no client data.
- `GET /reconciliation/queue?limit=25` — authenticated, bounded review candidates with their source evidence; read-only.
- `GET /reconciliation/review?limit=25` — authenticated read-only workspace data: candidates, unmatched purchases, and package-classification exceptions.
- `GET /appointments?startTime=…&endTime=…` — bounded owned schedule rows with stable appointment/contact identity and explicit authoritative, propagating, mirrored, or degraded truth state.
- `GET /appointments/readiness` — GHL appointment projection reconciliation, provider-neutral owned-authority reconciliation, and aggregate lifecycle-outbox state; no contact payloads.
- `POST /appointments/commands` — Worker-authenticated, recognized-Staff schedule capture and leased execution checkpointing under owned contact/service identity. It atomically rejects collisions, records append-only command evidence, and makes no provider call.
- `POST /appointments/attendance-commands` — Worker-authenticated, strict Staff attendance/no-show command boundary. It remains source-pinned shadow in this revision, so the route cannot write; the separately tested owned implementation is exact-revision, idempotent, atomic, append-only, and provider-free.
- `POST /notes/commands` — same-origin browser command boundary for a signed, named Eben or Garrett Staff session. It remains source-pinned shadow in this revision; the separately tested owned implementation creates immutable, exact-revision note history with reversible archive/restore and no provider fallback or destructive delete.
- `POST /tasks/commands` — same-origin browser command boundary for a signed, named Eben or Garrett Staff session. It remains source-pinned shadow in this revision; the separately tested owned implementation creates immutable exact-revision task history with complete/reopen and state-preserving archive/restore, no provider fallback, and no destructive delete.
- `POST /contacts/classification-commands` — same-origin browser boundary for a signed, named Eben or Garrett Staff session to add/remove one canonical tag or grant/revoke one recognized role. It remains source-pinned shadow; immutable command evidence is retained, exact old replay cannot overwrite later state, and provider-sourced classifications are never mutated.
- `POST /appointments/recovery-requests` — Worker-authenticated, Client-scoped capture of one pending review request for an exact signed missed-appointment revision. The strict payload excludes booking, entitlement, payment, decision, and message fields.
- `GET /appointments/recovery-requests?limit=25` — authenticated, bounded Staff readback of pending recovery reviews; read-only and no provider call.
- `POST /contacts/quiz-intake` — defense-in-depth Worker-authenticated normalized quiz source capture. It validates a strict allowlist, preserves exact owned identity, and atomically creates the shadow-nurture outbox; the request itself performs no provider or delivery call.
- `GET /quiz-intake/readiness` — authenticated aggregate-only source count, latest capture time, expired-retention count, and nurture-outbox state; no contact or quiz answers.
- `GET /quiz-intake/retention-readiness` — authenticated aggregate-only cross-store dry run over expired original intake evidence, CRM projections, every current contact foreign-key dependency, and Flow 1 automation copies. It exposes counts and a plan digest only; no identifiers, quiz answers, delete statement, execution route, scheduler hook, or provider action exists.

Retention execution remains intentionally unimplemented. The planner proves which original records and dependent copies would require coordinated treatment, while failing closed on incomplete schema coverage or unfinished dispatch. A separate privacy decision must define deletion versus redaction for immutable automation evidence and shared contact identities before any destructive path can be reviewed.
- `GET /communications/outbox/readiness` — authenticated aggregate-only legacy command availability plus the source-disabled owned email dispatch state and blockers; no contact, destination, subject, body, or provider identifiers.

The root dashboard does **not** accept a pasted worker bearer secret in the browser. Operator access is minted by `POST /dashboard-access-link` (bearer, server-side only) into a one-time five-minute handoff URL backed by an opaque high-entropy code in KV; redeeming `/dashboard-access/:code` sets a signed eight-hour HttpOnly browser session and never exposes `WORKER_AUTH_SECRET` in the URL. Staff opens this via `POST /api/staff-crm-mirror-access` (Eben JWT). The root server-renders aggregate counts and source health once the session is present, so the health summary remains visible even in a browser that cannot run the dashboard JavaScript. That session can read only the dashboard's GET endpoints; `POST /sync` and `POST /dashboard-session` continue to require the bearer credential on every request (machine/operator tooling, not the staff UI).

Approval actions require a separate signed 15-minute review session, created only with the bearer credential. Candidate acceptance/rejection and package classification record an `operational_events` audit record; neither action creates a ledger entry.
- `POST /sync` with optional `{ "sources": ["ghl", "stripe"], "limit": 25 }` — bounded manual import. Both provider integrations use `GET` only.

The normal first run is repeated bounded imports until both providers report `status: "succeeded"`, followed by reconciliation of unlinked purchases and the session ledger in a separate, reviewed change.

## Non-delivering Gmail evidence foundation

Migration `0016_gmail_provider_evidence.sql` adds append-only, mailbox-scoped storage for future Gmail provider submissions, accepted/failed/bounced outcomes, inbound messages, Gmail history observations, and attribution review. The pure repository preserves Gmail message/thread IDs and RFC `Message-ID`, `In-Reply-To`, and `References` evidence. Eben and Garrett are isolated by an exact `mailbox_actor` + `grant_owner` pairing; OAuth grants and token material are never stored in D1. Its API accepts that mailbox pairing as a separate trusted context which a future route must derive from signed Staff identity plus the verified actor-specific grant; mailbox identity is rejected inside the provider-evidence payload.

The evidence ingester itself does not call Gmail, register a watch or webhook, dispatch or compose mail, expose a browser route, or fall back to GHL. The dormant owned nurture dispatcher now appends an immutable `gmail_provider_submissions` row only after Gmail returns an actual provider message ID; the writer validates Garrett's exact mailbox, stable command reference, owned contact, provider IDs, and content, and rejects idempotency drift. Every nurture sequence remains source-level shadow and the independent delivery gates are absent, so this path is not active or deployed by the local build. A provider outcome can be attributed only when it matches that stronger submission proof. Outcomes remain delivery evidence rather than duplicate outbound message cards. The existing `outbound_delivery_attempts` rows are explicitly *not* submission proof because their only legal states are `not_sent_*`. Inbound messages enter Communication only after exact server-side RFC/thread attribution or a unique normalized sender match; ambiguous or conflicting evidence remains in `gmail_evidence_reviews`.
